# P14 — Per-detection confidence / reliability scoring

## Description

Nmap reports a port state — `open`, `closed`, `filtered`, `open|filtered` — but the
output treats every result as equally trustworthy, even though the *evidence*
behind them differs enormously. An `open` proven by a SYN-ACK or a real service
banner is near-certain. A `filtered` or `open|filtered` inferred purely from
**silence** (`no-response`) is a guess: on its own it is indistinguishable from a
dropped probe, rate-limiting, or a filtering middlebox.

P14 adds a normalized, machine-readable **reliability score** (0–10) and a coarse
**level** (`high` / `medium` / `low`) to every port, expressing how much the
reported state should be trusted. Nmap already exposes a service-name confidence
(`name_confidence`); P14 provides the equivalent for the *state* determination,
which had no such measure.

The score is surfaced in the native JSON output (P05) as two extra fields on each
port object:

```json
{
  "protocol": "tcp", "portid": 80, "state": "open",
  "reason": "syn-ack", "reason_ttl": 64,
  "reliability": 10, "reliability_level": "high",
  "service": { "name": "http", "product": "nginx", "method": "probed" }
}
```

## How the score is computed

Reliability is a function of the *reason* the state was reached (and, for open
ports, whether a real banner was read):

| Evidence                                                        | Score |
|-----------------------------------------------------------------|:-----:|
| Direct response from target (SYN-ACK, RST, conn-refused/accepted, UDP/proto/TCP response, port-unreachable, ARP/ND/echo reply, localhost-response) | 10 |
| ICMP error / administrative rejection (net/host/proto unreachable, admin-prohibited, time-exceeded, …) — filtering confirmed by a returned packet | 8 |
| `EACCES` while probing                                          | 7 |
| Set by a script/user, or inferred via idle (IP-ID) scan         | 6 |
| `no-response` — state inferred only from silence               | 3 |
| Unknown / other                                                 | 5 |

An `open` port whose service was actively **probed and matched** (a banner was
read) is forced to **10** regardless of scan type — reading a real service is the
strongest possible proof a port is open.

`reliability_level` is `high` for scores ≥ 8, `medium` for ≥ 5, and `low` otherwise.

## Why this matters

- **Triage:** consumers can prioritize `high`-reliability findings and treat
  `low`-reliability `open|filtered` results as "needs confirmation".
- **Foundation for defense detection:** honeypot/tarpit detection (P24) and the
  "real vs. middlebox-faked open ports" work (P25) build directly on this signal —
  a port that claims `open` but rests on weak evidence is exactly what those checks
  investigate. The scoring function (`compute_port_state_reliability`) lives in its
  own module (`port_reliability.{cc,h}`) so it can be reused by any output format or
  detection routine.

## Examples

```
# Show only low-confidence port states that warrant a closer look
nmap -sU -oJ - 10.0.0.5 | jq '.nmaprun.hosts[].ports[] | select(.reliability_level=="low")'

# Sort open findings by how trustworthy they are
nmap -sV -oJ - 10.0.0.0/24 | jq '.nmaprun.hosts[].ports[] | select(.state=="open") | {portid, reliability}'
```

## Verification

Reproducible test: [`tests/improvements/P14/run.sh`](../../tests/improvements/P14/run.sh).
It scans real localhost services and asserts the score discriminates evidence
quality: an open TCP service (banner) and a closed TCP port (RST) both score
`10`/`high`, while a UDP port that is `open|filtered` purely because it stayed
silent scores `3`/`low`.
