# P14 — Per-detection confidence / reliability scoring

Status: IN_PROGRESS
Branch: claude/nmap-enhanced-fork-yn7y8t (single-PR depth-first, documented deviation from per-feat branches)

## (A) DESIGN

### Problem
Nmap reports a port state ("open", "filtered", "open|filtered", "closed") but treats them all as
equally trustworthy in the output, even though the *evidence* behind them varies enormously:
- "open" proven by a SYN-ACK or an actual service banner is near-certain.
- "open|filtered" or "filtered" inferred purely from **silence** (`no-response`) is a guess — it could
  equally be a dropped packet, rate-limiting, or a middlebox.
Consumers (and later honeypot/middlebox detection, P24/P25) need a normalized, machine-readable measure
of how reliable each state determination is. Service-name confidence (`name_confidence`, 0-10) already
exists, but there is no equivalent for the **state** itself.

### Approach
Add a small, reusable scoring function that maps the port's `state_reason_t` (how the state was decided)
plus available service evidence into a 0-10 reliability score and a coarse level (high/medium/low):
- Direct positive responses (SYN-ACK, RST, conn-refused/accepted, UDP/proto/TCP response, port-unreach,
  ARP/ND/echo replies, localhost-response) → 10: the target actively proved the state.
- ICMP unreachable / prohibited errors (net/host/proto unreach, admin-prohibited, etc.) → 8: filtering
  is confirmed by an error packet (not just silence).
- Script/user-set or idle-scan inference → 6.
- `no-response` (state inferred from silence) → 3.
- Unknown → 5.
- Boost: an `open` port whose service was actively **probed and matched** (banner) → forced to 10.

Level: >=8 high, >=5 medium, else low.

### Files
- NEW `port_reliability.h` / `port_reliability.cc` — `compute_port_state_reliability()` + `reliability_level()`.
  Reusable by JSON output now and by P24/P25 later.
- `output_json.cc` — add `reliability` (0-10) and `reliability_level` to each port object.
- `Makefile.in` — add `port_reliability.o`.
- Doc + test.

### Why surface in JSON (not the normal table)
The normal/grepable/XML tables have many downstream parsers and fixed layouts; adding columns risks
regressions. JSON is the machine-readable surface where confidence is actually consumed, and it is the
natural home (extends P05). The scoring function is independent of output format so other formats/consumers
can adopt it later without rework.

### Test strategy (phase C)
Scan localhost services and assert the score discriminates evidence quality:
- open TCP (real http server, banner) → reliability == 10, level "high".
- closed TCP (unused port, RST) → reliability >= 8, level "high".
- UDP port with no response (open|filtered via silence) → reliability <= 4, level "low".
